# Gateway accounting and settlement

The merchant program binds the authenticated tenant, processor account, currency and beneficiary alias. The first admitted payment or accepted independent source binds the beneficiary within the financial book. Access to that book under a different beneficiary grant is rejected. The journal tracks the merchant’s attributed position in integer minor units. It grants no payout or beneficiary-editing authority. Only the processor worker posts captures and merchant-requested refunds, atomically with the verified operation outcome.

| Route | Required authority and contract |
| --- | --- |
| POST /v1/settlement-statements | Statement importer. Supply payout_id, bank_trace, beneficiary, currency, net_minor, source_digest and lines. Each immutable line has line_id, kind, reference, signed amount_minor and, for an adjustment, parent_reference. IDs are scoped to a merchant program. Provider line IDs must be stable across imports. |
| POST /v1/bank-entries | Independent bank importer. Supply entry_id, bank_trace, beneficiary, currency, signed amount_minor and source_digest. A returned posting also specifies return_of_bank_entry. All input here represents a booked bank movement. Pending instructions cannot be used as evidence. |
| POST /v1/payouts/{id}/prepare-close | Finance preparer. Supply bank_entry_id matching the statement trace, beneficiary, currency and signed net. A zero-net statement requires an explicitly empty bank_entry_id. Preparing exclusively allocates the bank movement. |
| POST /v1/payouts/{id}/approve-close | Independent reviewer. Supply the exact returned proposal_id. The preparer and both source importers cannot approve. Recheck the financial evidence in the posting transaction. |
| GET /v1/payouts/{id} | Merchant, finance or reviewer. Returns the source manifest, close status and approval trail. Later bank returns and processor recredits are reported separately from the original matched bank posting. |
| GET /v1/journal | Merchant, finance or reviewer. Response has entries, through_sequence and next_after. Continue with after=next_after and through=through_sequence to traverse a fixed snapshot. limit defaults to 100 and allows up to 250. |

Imports return 201 for creation and 200 for replay of the identical source ID and terms. A 409 signals conflicting identity, incomplete evidence, ambiguous bank match or reused allocation. A 422 signals inconsistent amounts, unsupported fields of economic meaning, or invalid program data. Invalid JSON or unknown fields return 400. A source digest is a lowercase SHA-256 hex string identifying the source document. Trusted importers must independently verify the original artifact, map its booked records and preserve it under the applicable retention policy. The local credential authenticates the importer; it cannot independently attest to the origin of an arbitrary uploaded digest.

## Routed processor accounts

A routed settlement manifest carries both `route_id` and `provider_account`. Use the statement credential issued for that merchant and that exact route/account. Source imports under another route's credential return 403. A new source account requires an existing merchant route enrollment. The historical unbound credential continues to accept unbound statements and can match only historical unbound processor records.

Use `/v1/routes/{route_id}/accounts/{provider_account}/payouts/{payout_id}` for a routed payout. Append `/prepare-close` or `/approve-close` for its two close actions. Each independent source can reuse the same native payout ID, capture reference, refund reference and statement line ID. The route and provider account select the source record. Payout IDs on the original `/v1/payouts/{id}` path remain in the historical namespace.

The journal has one sequence per merchant program and currency. Routed processor entries include their route and provider account. Captures additionally carry the selected method and connector and, when reported by the processor, the observed card brand. A chargeback or source-initiated refund puts a hold on the matching source's original capture. Bank records remain merchant-wide. A funding claim must trace to exactly one bank posting and one remittance across all routes. An additional candidate received after close leaves the original posting and approval intact. Reading that payout returns `funding_match_ambiguous: true`, and conflicting evidence blocks a later recredit. Recredit following a bank return must link to the matched source route.

For a signed correction to one booked fee in an approved routed payout, use the separate correction workflow. It preserves the original close and produces a bank-confirmed posting for the merchant importer. [Booked fee corrections and reproducible fixture](booked-fee-corrections.md)

## Movement types

- A **capture** is positive. A **refund** is negative. Each matches the exact original processor movement reference and amount.
- **fee** and **chargeback** are negative. **fee_rebate** is positive. Each links to an original capture. A **chargeback_reversal** is positive and refers to the original chargeback reference. Unknown parents hold the import. A dispute notice without a booked debit produces no financial posting through this endpoint.
- A **source_refund** is an independently booked refund outside dakim’s original instruction. Link it to the original capture and give it its own reference and negative value. It places a hold on voluntary refunds and first fulfilment against that capture.
- An **additional_capture** identifies an independently evidenced excess collection against an original capture. Both charges are journaled, with one original retail operation. The payout reports exception_ids and open_exceptions. Partial **refund_excess_capture** movements use negative amounts, distinct external references and the additional capture reference as parent. The payout cannot close until the observed restitution equals the excess. Retain each line and case identifier.
- A bank return uses a new posted bank ID, new trace and opposite signed amount, with return_of_bank_entry identifying the original bank movement. The difference remains in bank_return_under_investigation. A later settlement **return_recredit** line must link to the bank return's entry ID, use the opposite direction and remain within the return. Only a new, independently matched payout establishes receipt of replacement funds.

Each posting balances by program and currency. Bank imports initially post to observed_merchant_bank against unallocated_bank_movements. An ordinary close clears transit and the bank suspense account. A matched payout may later be returned; its original evidence and approval remain visible. Multiple bank movements or multiple remittances with the same trace, beneficiary, currency and amount prevent a new close. The current importer supports a bounded one-statement / one-bank-entry close and zero-net statements; complex split or consolidated funding needs a qualified source-specific allocator. Conflicting or unsupported manifests must be retained by the importer for investigation. Posted movements cannot be edited through the API.
