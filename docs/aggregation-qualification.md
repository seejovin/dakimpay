# dakim pay rail aggregation

**Release decision.** The four-provider installation is qualified for local synthetic merchant integration. External sandbox and production acceptance remain open. The payer chooses a payment method; dakim pay chooses an eligible processor enrollment. A card transaction also has an observed brand after authorization. These are independently recorded so an acquiring route can change for future orders without altering an existing charge or its refund.

Each merchant grant identifies its account, currency, outlets, reader assignments and transaction ceiling. The route catalog adds method, channel, amount range, connector, upstream account, currency and priority. The default fixture uses USD. Availability for additional markets and currencies requires the selected partner's actual merchant entitlement. A priority value only describes where a new eligible instruction should go.

## Merchant workflow

1. Discover enrolled payment methods with `GET /v2/payment-methods?channel=hosted&amount_minor=1234`. The amount is in the authenticated program’s currency. An amount-specific inquiry checks the current operating controls. The final create checks them again.
2. Submit `POST /v2/payment-intents` with an idempotency key that survives retries. Include order ID, allocation ID, method, channel, outlet, integer amount and currency. Preserve the returned operation ID and bound route. For terminal sales additionally supply the assigned reader ID.
3. Poll the original operation or consume signed merchant events. For hosted transactions send the buyer to the original checkout URL. A returned browser does not settle the merchant’s order.
4. Before releasing goods use the original payment’s `/release-evidence` endpoint. A capture can exist while a refund, dispute, financial exception, conflicting card brand or incomplete evidence prevents fulfilment. An Antom payment inquiry alone cannot prove that no outside reversal exists.
5. Refund the original charge with its merchant refund reference. The gateway retains the original upstream account and route through outages, restarts and policy changes. For the processor’s statement use a credential authorized for that source. The bank observation, preparer and approving reviewer are separate authorities.

## Failure and settlement exercises

- An original USD 12.34 Visa sale was approved at the primary acquirer while the gateway was down. That acquirer was then taken offline and its route suspended. A new hosted sale used the secondary. Recovery and the original refund used the primary. Each acquirer’s own database was examined for the resulting movements.
- Six original captures and three linked refunds produced four frozen remittances. Every provider used the same native payout ID, `daily-001`. Separately scoped imports and four-eye review matched **USD 16.04** at the primary card acquirer, **4.88** at the secondary, **2.90** for WeChat Pay and **5.10** for Alipay. The total was **USD 28.92**. The four bank records were synthetic.
- PostgreSQL and Google’s official Spanner emulator exercise the gateway’s financial transaction model. The four downstream virtual institutions each maintain a PostgreSQL database. All run on one local host in this fixture.
- In separate provider-shaped HTTP tests, Stripe and Antom each processed a merchant payment and original refund through the gateway and routing API. Stripe queried linked capture, refund and dispute evidence. Antom authenticated the response and confirmed the original refund but withheld goods release when full reversal and dispute evidence was unavailable. No real partner account participated.
- Eight HTTP clients exercised all four providers with repeated create, approval and refund requests. Each database backend produced exactly **32 captures and eight refunds**, with ten movements per provider. The combined journals showed $30.16 for Mimi and $31.52 for the second merchant after refunds. A PostgreSQL run took 2.059 seconds from first request through reconciliation. A Spanner emulator run took 29.965 seconds; five additional create attempts and one additional refund attempt reused their original request keys after transport uncertainty. These are single local runs with test data, not a production throughput or latency claim.
- The independent worker-lane test held a card-provider inquiry open while a newly admitted Alipay payment reached capture. A route suspension blocks new and unsent charge submissions. Refunds and recovery queries remain bound to their original route.
- The macOS ARM64 binaries are cross-built and inspected. Native macOS execution and Apple notarization remain unverified. The executable Linux release is tested from extraction.

## Decision for live acquiring

Before a real merchant can accept funds, the operator must establish the target market and funds flow, product approvals, contracted acquiring and wallet accounts, settlement bank access, key custody, independent security assessment and staffed operating controls. Validate each selected account end to end with remote approvals, a lost response, reversals, refunds, disputes, independently sourced remittances and booked bank postings. Resolve funding timing, scheme rules and settlement currency against the agreement. Certify the chosen physical reader with its acceptance partner before using physical cards.

Production scale, disaster recovery, adversarial assurance, merchant underwriting and losses, cross-currency funding, cost-based or approval-rate routing, and equivalence to the operating capabilities of Stripe, Alipay or WeChat Pay have not been demonstrated. Default route selection uses explicit eligible priorities. Direct commercial access to Visa, Mastercard, American Express, WeChat Pay or Alipay requires its corresponding agreement and evidence.
